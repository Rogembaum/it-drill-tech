# I56 — Маршрутизация: супер-критичное только локально, остальное — в облако

**Направление:** 14 inference.

## Сценарий
Политика разделения разработки: критичные репозитории и КТ обрабатываются только локальными моделями, остальное идёт в облако, чтобы не занимать дефицитные GPU. Текущий роутер при падении локального vLLM отправляет всё в облако, а запрос без классификации считает публичным. Напиши маршрутизатор с fail-safe поведением.

## Контракт
```python
policy = {
    "critical_repos": ["payments-core", "risk-engine"],
    "cloud_tenants": ["team-web", "team-data"],
    "local": {"code": "qwen-coder-local", "chat": "qwen-local"},
    "cloud": {"code": "or-deepseek-v3.1", "chat": "or-glm-4.6"},
}
route({"repo": "payments-core", "classification": "internal", "task": "code", "tenant": "team-pay"},
      policy, health={"local": True, "cloud": True})
# {"status": 200, "target": "local", "model": "qwen-coder-local", "reason": "critical_repo"}
```

| Условие | Результат |
|---|---|
| `classification == "secret"` | 403 `secret` — такие данные не должны были дойти до шлюза (F52 block) |
| нет `classification` | считаем `kt`: неизвестное — значит критичное |
| `task` нет в политике | 400 `task` |
| репозиторий в `critical_repos` или `kt` | только `local`; локальный недоступен — 503 `local_unavailable`, **никакого облака** |
| tenant не в `cloud_tenants` | только `local` (reason `no_cloud_access`); недоступен — 503 |
| остальное | `cloud` (reason `cloud_default`); облако недоступно — `local` (reason `cloud_fallback`); оба недоступны — 503 `no_backend` |

## Требования к результату
Критичный репозиторий или kt — только local, при недоступности 503 без облака; секреты — 403; нет классификации — как kt; остальное — cloud, при недоступности облака local; команды без допуска к облаку — local; неизвестная задача — 400; в ответе есть reason.
